# Proposed changes for v0.3: gaps found building the issuer, vbot and the integrations

Status: **proposed** · 18 November 2026

Building the staging issuer ([`veridact-issuer`](../../issuer)), the agent client ([`vbot`](../../vbot)) and the
gateway integrations ([Lambda authoriser](../../integrations/aws-lambda), [Keycloak bridge](../../integrations/keycloak))
against v0.2 turned up places where the spec names a step but not its wire format, so an issuer and a client have to agree
on something the spec does not say. Each item states the gap, what the reference implementations do today, and the
text proposed for v0.3. The end-to-end tests in [`e2e/`](../../e2e) encode these choices.

Nothing here changes what a relying party verifies: credentials from the staging issuer pass the unmodified
`veridact-verify` and its conformance vectors.

## 1. The key-binding JWT that replaces the CSR

**Gap.** "A signed key-binding JWT replaces the CSR" and "signed by the agent key over the order URL and a fresh
nonce" name the idea but not the token.

**Today.** A compact JWS, ES256, `typ: veridact-kb+jwt`, with `kid` naming a key of the subject DID:

```json
{ "iss": "<subject DID>", "aud": "<this order's finalize URL>", "nonce": "<the ACME nonce of this finalize request>", "iat": 1794981300 }
```

The nonce is the one in the outer JWS's protected header, so the proof cannot be replayed into another request.
`iat` must be within 5 minutes. For an Agent Credential the key must be under the agent DID's `authentication`
(it becomes `cnf`); for an Operator Credential, under the operator DID's `assertionMethod` (the key that signs
delegations).

**Proposed text.** Define the token as above in "Issuance protocol".

## 2. The Domain Linkage Credential for did-config-01

**Gap.** did-config-01 checks "a Domain Linkage Credential at /.well-known/did-configuration.json", without saying
which format, or which DIDs a domain may link.

**Today.** The [DIF Well Known DID Configuration](https://identity.foundation/.well-known/resources/did-configuration/)
JWT form, unchanged, so existing wallet and domain-linkage tooling works. The issuer accepts a linkage only for
`did:webvh:{SCID}:{domain}` (the DID at the root of the same domain), signed by an `assertionMethod` key, with
`origin` equal to `https://{domain}`. A domain cannot vouch for a DID hosted elsewhere.

**Proposed text.** Name the DIF JWT form, and state that the operator DID must be `did:webvh:{SCID}:{domain}`.

## 3. delegation-01 and the Delegation Credential

**Gap.** The Delegation Credential's claims are listed in a table, but not named, and the challenge response
format is not given.

**Today.** The client POSTs `{"delegation": "<vc+jwt>"}` to the challenge. The credential:

```json
{
  "type": ["VerifiableCredential", "VeridactDelegationCredential"],
  "issuer": "<operator DID>",
  "credentialSubject": {
    "id": "<agent DID>",
    "scopes": ["fs:claims:read-status"],
    "limits": { "currency": "ZAR", "perPayment": "500.00", "perDay": "2000.00" },
    "accountableRole": "Head of Digital Claims",
    "maxLifetime": 28800,
    "environment": "staging",
    "audiences": ["https://api.bank.example"]
  }
}
```

`environment` must match the issuer's, so a staging delegation cannot be used to obtain production credentials.
The issuer rejects scopes outside the tier's policy (it is stricter than a verifier, which drops unknown scopes),
and a lifetime over 90 days.

**Proposed text.** Name these claims, and add the environment rule.

## 4. A delegation only works for the account that holds the Operator Credential

**Gap.** delegation-01 requires "an operator DID that holds a valid Operator Credential", but not that the ACME
account placing the order is the operator's. Without that, whoever holds the agent key and a copy of its
delegation (a compromised agent host, say) could keep renewing from an account of their own, out of the
operator's sight and beyond its account controls.

**Today.** The issuer accepts a delegation only from the account that obtained the operator's Operator Credential.

**Proposed text.** "The account placing an agent order must hold a valid Operator Credential for the delegation's
issuer."

## 5. Where an agent DID may live

**Gap.** The identifier table shows the two patterns, but the issuer is not told to enforce them.

**Today.** The issuer accepts an agent DID only as `did:webvh:{SCID}:{operator domain}:agents:{id}` on a domain in
the operator's credential, or `did:webvh:{SCID}:{hosted prefix}:{account slug}:{id}` on the issuer's hosting.
The account slug is opaque and random, like agent ids.

**Proposed text.** Make both patterns normative for issuers.

## 6. Veridact-hosted agent DIDs

**Gap.** "For operators that cannot host DID logs" has no upload mechanism.

**Today.** `POST {veridactDidHosting}/{agent id}` (a directory entry), ACME-signed by the account, with
`{"log": "<did.jsonl>"}`. The issuer verifies the whole log before serving it, accepts only DIDs under the
account's own slug, and accepts updates only if they extend the stored log: history is never rewritten.

**Proposed text.** Add the endpoint to the ACME-A table and the directory metadata.

## 7. Orders, tiers and lifetimes

**Gap.** How a client asks for a tier or a lifetime, and how many identifiers an order may carry.

**Today.** One identifier per order. `new-order` takes optional `tier` (default: the issuer's lowest) and
`lifetime` in seconds. An Agent Credential's lifetime is the smallest of: the request (default 8 hours), the
delegation's `maxLifetime`, the trust list's maximum, and the time left on the delegation and on the Operator
Credential. Under 5 minutes, the issuer refuses.

**Proposed text.** State these rules in "Issuance protocol".

## 8. The transparency log receipt and entry id

**Gap.** The download "returns application/vc+jwt plus the transparency log receipt", but a vc+jwt body has no
place for one. The Operator Credential carries a "transparency log entry id" with no format.

**Today.** The receipt travels in a `Veridact-Log-Receipt` response header (base64url JSON). Entry ids are
`{log id}/{index, 9 digits}`. Because the Operator Credential must name its entry before it is signed, the issuer
serialises issuance and signs the next index in.

**Proposed text.** Specify the header and entry id format. Month 2's tile-based log replaces the hash-chained
stand-in and adds inclusion proofs to the receipt.

## 9. The audience an agent signs for

**Gap.** In pattern B the challenge carries realm, nonce, tier and scope, but not the `aud` the relying party
expects.

**Today.** vbot signs for the origin of the URL it called (`https://api.bank.example`), and the sandbox and the
sidecar are configured with that origin as their audience.

**Proposed text.** "In pattern B, `aud` is the origin of the request URL." Alternatively, add `aud` to the
challenge, at the cost of letting a man-in-the-middle choose it.

## 10. The two-person rule before Approver Credentials exist

**Gap.** Single payments above R1,000 need a second approver, but the staging issuer does not accept Approver
Credentials yet (the operator DID signs delegations itself).

**Today.** The issuer refuses any delegation whose `perPayment` exceeds R1,000. That keeps the rule intact rather
than silently skipping it.

**Proposed text.** None: this is an implementation gap, closed when approver chains land.

## 11. Pattern A: where the nonce comes from

**Gap.** Token exchange has no challenge step, yet check 1 requires a nonce "issued here".

**Today.** The token endpoint answers a request without `subject_token`, or with a spent or unknown nonce, with
`400 {"error": "use_veridact_nonce"}` and a `Veridact-Nonce` response header, mirroring how DPoP servers hand out
nonces (RFC 9449 section 8). The agent signs a presentation for that nonce and retries. The presentation's `aud`
is the token endpoint's origin.

**Proposed text.** Add this exchange to pattern A in "Verification at the relying party".

## 12. Pattern A: token type and key binding

**Gap.** The spec says the presentation travels as `subject_token` and the access token is DPoP-bound, but names
no `subject_token_type` and does not say which key the DPoP proof must use.

**Today.** `subject_token_type=urn:veridact:params:oauth:token-type:vp+jwt`. The DPoP proof must be made with the
agent's Veridact key, the one the Agent Credential's `cnf` names, so the access token is bound to the same key as
the credential. The [Keycloak bridge](../../integrations/keycloak) enforces both, then uses Keycloak's JWT
Authorization Grant (RFC 7523) so Keycloak issues the token under its own policies.

**Proposed text.** Register the token type URN in the spec, and require the DPoP key to equal the `cnf` key.

## Smaller choices

- **Status list indexes** are allocated at random within a list, so a credential's index reveals nothing about
  when it was issued. Agent and Operator Credentials use separate lists.
- **renewal-info** is keyed by the credential's UUID, because ARI's certificate identifier does not apply.
- **Challenges validate synchronously** when the client responds, and a failed challenge invalidates the order,
  as in RFC 8555.
- **Revocation** re-signs the affected status list at once, so the 5-minute visibility rule is met by the issuer
  and the remaining delay is the verifier's cache.
