# Proposed changes for v0.5: SD-JWT VC, OAuth-native identifiers and known assistants

Status: **proposed** · 22 November 2026 · decision to proceed taken by the lead maintainer; open for review

v0.5 moves Veridact from W3C VC Data Model 2.0 with `did:webvh` to the formats the IETF OAuth working group is
standardising: **SD-JWT VC** for credentials, the **Token Status List** for revocation, **HTTPS identifiers** with
**Client ID Metadata Documents** for agents, and **Attestation-Based Client Authentication** as a third way to
present. It also adds **known-assistant entries**, so mainstream assistants (Claude, ChatGPT, Gemini, Copilot) can
be identified and withdrawn without their platforms taking part.

What does **not** change: the trust model, the tiers, ACME-A as the issuance protocol, delegation from appointed
approvers with the two-person rule, sub-agent attenuation, short lifetimes, the transparency log, the trust
registry, Agent Certificates, archival verification, reason codes, and the rule that relying parties never call
an issuer.

## Why

| Reason | Detail |
|---|---|
| One stack for banks | A bank already runs OAuth. Every v0.5 artefact is a JWT its authorisation server, gateway and HSM already handle, verified with keys from an HTTPS URL. There is no DID resolver, no did:webvh log parser and no JSON-LD context. |
| Where the standards are going | SD-JWT VC is in IESG evaluation, the Token Status List is in the RFC Editor queue, and attestation-based client authentication and Client ID Metadata Documents are OAuth working group documents. The EU digital identity wallet uses SD-JWT VC. |
| Selective disclosure | An agent proves "verified, South African, Organisation tier" without disclosing its registration number to every API it calls. |
| One identity URL | The agent's `client_id` (a CIMD URL) is also its Veridact identifier, so OAuth client identification and Veridact verification name the agent the same way. Valet's technical design already asks for this (§9.2). |
| Mainstream assistants | v0.4 has no way to say anything about Claude or ChatGPT, whose platforms will never run ACME-A. Banks need it now (Valet's Lane A). |

## What we give up, and how we cover it

| Lost with did:webvh | Cover in v0.5 |
|---|---|
| Pre-rotation of DID update keys, so a stolen key can't take over an identifier | **Key events in the transparency log.** Every operator and agent key change is logged before it takes effect. Monitors alert the operator within minutes, and verifiers refuse a key with no log entry (§1.3). |
| Witness co-signing of issuer key history | Issuer keys are listed in the governance-signed trust list, which already has witnesses and an overlap period. That is now the only source of issuer keys. |
| W3C VC ecosystem interoperability | **Accepted trade-off.** Banks were the target, not wallets. An issuer may still issue a W3C VC copy of a credential later (a `formats` value), with no change to verification. |

## 1. Identifiers

| Party | v0.4 | v0.5 | Keys published at |
|---|---|---|---|
| Issuer | `did:webvh:…:veridact.net:issuers:{tier}-{epoch}` | `https://veridact.net/issuers/{tier}-{epoch}` | `/.well-known/jwt-vc-issuer` on the issuer URL (`jwks`). The trust list pins the same keys. |
| Operator | `did:webvh:{SCID}:{domain}` | `https://{domain}` (a validated domain) | `https://{domain}/.well-known/veridact-operator.json`: delegation-signing keys |
| Agent, operator-hosted | `did:webvh:…:{domain}:agents:{id}` | `https://{domain}/agents/{id}`: a **Client ID Metadata Document** | The CIMD's `jwks` |
| Agent, Veridact-hosted | `did:webvh:…:dids.veridact.net:{slug}:{id}` | `https://agents.veridact.net/{slug}/{id}`: a CIMD served by Veridact | The CIMD's `jwks` |

### 1.1 Agents are OAuth clients

An agent identifier is a CIMD URL. Its document follows draft-ietf-oauth-client-id-metadata-document:

- `client_id` equals the URL, compared as a plain string
- `jwks` holds the agent's authentication keys
- `token_endpoint_auth_methods_supported` includes `attest_jwt_client_auth_dpop`, plus `private_key_jwt` where
  the agent uses it

The same URL is the `sub` of the Agent Credential and the `client_id` at every bank. Ids stay opaque random
strings, because the documents and the log are public.

### 1.2 Operators

An operator is its validated domain. The domain serves `veridact-operator.json`:

- `operator`: the URL itself
- `jwks`: delegation-signing keys
- `agents`: optional; the agent URL prefixes it runs

This replaces the DID log and the Domain Linkage Credential.

### 1.3 Key events

A new log entry type, `key-event`, records:

- the subject (an operator or agent URL)
- the key thumbprint
- the action: `add`, `retire` or `compromise`
- the time
- a signature by the operator's account key

Issuers append it when the operator publishes or retires a key through ACME-A (§4).

**Verifiers refuse a key with no `add` event, or with a `retire` or `compromise` event older than the
credential.** This gives most of did:webvh's protection against key takeover, auditable by anyone. A thief who
edits a CIMD document still can't get a new key accepted without an ACME-A request from the operator's account,
and that request is logged and monitored.

## 2. Credentials: SD-JWT VC

All credentials are SD-JWT VCs: `typ` `dc+sd-jwt`, ES256, issuer keys resolved through JWT VC Issuer Metadata, or an
`x5c` chain where a relying party pins X.509 anchors. `iat`, `nbf` and `exp` carry the validity window, so ordinary
gateways can enforce expiry. Claims marked (SD) are selectively disclosable.

| Credential | `vct` | Issued by | `sub` | Claims | Lifetime |
|---|---|---|---|---|---|
| Operator Credential | `https://veridact.net/vct/operator/v1` | Issuer | Operator URL | `tier`, `domains`, `log_entry`, `cnf` (the operator's delegation key), `status`; (SD) `legal_name`, `registration` (CIPC number or LEI), `jurisdiction` | Unchanged: 90 days or 12 months |
| Approver Credential | `https://veridact.net/vct/approver/v1` | Operator | Pseudonymous approver id | `role`, `scopes`, `ceiling`, `cnf` (the approver's passkey-backed key) | Unchanged |
| Delegation Credential | `https://veridact.net/vct/delegation/v1` | Approver(s), countersigned by operator key | Agent URL | Unchanged claims: `scopes`, `limits`, `accountable_role`, `max_lifetime`, `environment`, `audiences`, `certificate_max_lifetime` | Up to 90 days |
| Agent Credential | `https://veridact.net/vct/agent/v1` | Issuer | Agent URL | `operator`, `operator_credential` (its `jti`), `operator_status` (the Operator Credential's status reference), `tier`, `scopes`, `limits`, `accountable_role`, `cnf.jwk`, `status`; (SD) `operator_legal_name`, `operator_registration`, `operator_jurisdiction` | Unchanged: default 8 hours, maximum 24 |
| Known-Assistant Credential (new, §6) | `https://veridact.net/vct/known-assistant/v1` | Issuer | Platform identifier | See §6 | Up to 90 days |

**The Agent Credential now carries the operator facts a relying party needs**, copied and signed by the issuer at
issuance. So a presentation no longer has to carry the Operator Credential. The relying party checks both status
entries: `status` for the agent, and `operator_status` for the operator. Revoking the operator still stops all its
agents within 5 minutes.

An Agent Credential, decoded (issuer-signed part; disclosures omitted):

```json
{ "alg": "ES256", "typ": "dc+sd-jwt", "kid": "org-2026b-3" }
.
{
  "iss": "https://veridact.net/issuers/org-2026b",
  "vct": "https://veridact.net/vct/agent/v1",
  "jti": "urn:uuid:5f0c2d6e-8b1a-4c3e-9f27-1d4a6b8e0c55",
  "sub": "https://operator.example/agents/a7f3k2",
  "iat": 1792483200, "nbf": 1792483200, "exp": 1792512000,
  "operator": "https://operator.example",
  "operator_credential": "urn:uuid:9d2e7a10-3c44-4b8f-a6e1-0f5b2c7d9e31",
  "operator_status": { "status_list": { "idx": 9123, "uri": "https://status.veridact.net/org/operators/2" } },
  "tier": "organisation",
  "scopes": ["fs:claims:read-status", "fs:quotes:create"],
  "accountable_role": "Head of Digital Claims",
  "limits": { "currency": "ZAR", "per_payment": "500.00", "per_day": "2000.00" },
  "cnf": { "jwk": { "kty": "EC", "crv": "P-256", "x": "…", "y": "…" } },
  "status": { "status_list": { "idx": 48213, "uri": "https://status.veridact.net/org/agents/7" } },
  "_sd": ["…", "…", "…"], "_sd_alg": "sha-256"
}
```

Claim names move to snake_case, the JWT convention (`perPayment` becomes `per_payment`). Amounts stay decimal
strings.

## 3. Presentation: SD-JWT with Key Binding

The `vp+jwt` presentation is replaced by an **SD-JWT+KB**: the Agent Credential, the disclosures the relying party
asks for, and a Key Binding JWT signed by the `cnf` key.

- KB-JWT: `typ` `kb+jwt`, claims `aud` (this relying party), `nonce` (issued here), `iat`, and `sd_hash`
- Lifetime rule unchanged: the relying party accepts a KB-JWT only within 120 seconds of its `iat`, plus skew
- Disclosure by policy: a route says which (SD) claims it needs (for example, `operator_legal_name` for a
  consent screen). The verifier refuses a presentation that hides a required claim (`CLAIMS_NOT_DISCLOSED`, a new
  logged reason; the public code is `AUTH_FAILED`)

**Sub-agents.** The `veridact-subgrant+jwt` grant chain is unchanged. It travels in the KB-JWT as `veridact_grants`,
and the KB-JWT is signed by the last grant's key. We track draft-ietf-oauth-delegate-sd-jwt (now a working group
document) and expect to adopt it for sub-agents once it stabilises.

## 4. ACME-A changes

| Item | v0.4 | v0.5 |
|---|---|---|
| Agent identifier type | `agent-did` | `agent`, value the agent URL |
| Operator key proof | `did-config-01` | `operator-keys-01`: the issuer fetches `/.well-known/veridact-operator.json` from three vantage points and checks it lists the key that signs the order's delegation |
| Agent key proof | Key in the DID log's `authentication` | `client-metadata-01`: the agent URL serves a CIMD whose `client_id` equals the URL and whose `jwks` contains the key in the key-binding JWT |
| Key-binding JWT `kid` | A DID URL | The JWK thumbprint (RFC 7638) |
| Download | `application/vc+jwt` | `application/dc+sd-jwt` (the issuer-signed JWT with all disclosures), with the log receipt header unchanged |
| `formats` | `vc+jwt`, `x509` | `dc+sd-jwt` (default), `client-attestation` (§5.3), `x509` |
| Veridact-hosted identifiers | DID log upload | CIMD upload to `{veridactAgentHosting}/{id}`: the issuer serves it, accepting only keys with a logged `add` event |
| Key events | None | `POST /key-event` (ACME-signed): add or retire an operator or agent key; logged before it takes effect |

dns-01, delegation-01, accounts, orders, nonces, ARI renewal and rate limits are unchanged.

## 5. Presenting to a relying party

| Pattern | How | Fits |
|---|---|---|
| **A. Token exchange** (unchanged shape) | `subject_token` = the SD-JWT+KB, `subject_token_type` = `urn:veridact:params:oauth:token-type:sd-jwt-kb`, with a DPoP proof made with the `cnf` key | Banks with an authorisation server in the path (Keycloak bridge, PingFederate, Entra) |
| **B. Gateway** (unchanged shape) | `401` with `WWW-Authenticate: Veridact nonce=…`; retry with `Authorization: Veridact sd-jwt="<SD-JWT+KB>"` | Gateways without an authorisation server |
| **C. Client attestation** (new) | The agent authenticates to the bank's authorisation server with `attest_jwt_client_auth_dpop`: a Veridact-issued **Client Attestation** in `OAuth-Client-Attestation`, and its DPoP proof as the proof of possession | Banks whose authorisation server supports attestation-based client authentication; the default for Valet's Lane B |

### 5.3 The Client Attestation form

When an order's `formats` includes `client-attestation`, the issuer also signs an `oauth-client-attestation+jwt`
with the same `sub` (the agent URL), `exp`, `iat`, `cnf.jwk` and `status` as the Agent Credential. It adds
`veridact`, holding `operator`, `tier`, `scopes`, `limits`, `operator_status` and the Agent Credential's `jti`. It
has no selective disclosure; it carries only what an authorisation server needs to admit the client. It is
logged with the Agent Credential, and revoking either revokes both.

### 5.4 Tokens

The pattern A token shape is unchanged, except that `act.sub` is the agent URL, and `act.sub_profile` is
`ai_agent`, following draft-mcguinness-oauth-actor-profile. In Veridact Valet, `sub` is the bank's own customer
identifier, and the `veridact` claim carries `tier`, `limits`, the credential ids and `consent`.

## 6. Known-assistant entries

Mainstream assistants connect to banks as one OAuth client per platform. They will not run ACME-A or hold a
Veridact key. Veridact therefore verifies the platform's operator itself and issues a credential *about* the
platform, which relying parties check locally.

| Claim | Meaning |
|---|---|
| `sub` | The platform identifier: a CIMD URL (Claude, ChatGPT), or a stable name where the bank registers the client itself (Gemini, Copilot) |
| `client_metadata_urls` | Every CIMD URL the platform uses, for example Claude's and Claude Code's |
| `operator` | Legal name, jurisdiction and verification date of the platform operator |
| `redirect_hosts` | The hosts its OAuth callbacks use |
| `token_endpoint_auth` | How it authenticates: `none`, `private_key_jwt` with its JWKS URL, or a bank-registered secret |
| `max_level` | Veridact's recommended ceiling. A relying party may lower it, never raise it through Veridact |
| `status` | A Token Status List entry: valid, withdrawn or suspended |

- **Issuance.** Organisation tier only. Validation is documentary (the platform's published metadata, its legal
  entity and its published egress), by a reviewer; there is no ACME-A challenge. Logged like any credential.
- **Use.** At client registration and on every token request, the bank's authorisation server maps the client
  to a valid entry; the consent screen shows the verified operator name.
- **Kill switch.** Suspending an entry stops that assistant at every relying party on its next check. The
  governance authority publishes the criteria for withdrawal and suspension. The platform can see its entry, is
  told before withdrawal where possible, and can dispute it.
- **Limits.** An entry identifies a platform, never a user or an instance. It never raises an assurance tier.

## 7. Revocation: Token Status List

Bitstring Status Lists are replaced by Token Status Lists (`typ` `statuslist+jwt`), with these rules:

- Two bits per entry: `0x00` VALID, `0x01` INVALID (revoked), `0x02` SUSPENDED
- `ttl` of 300 seconds
- Lists signed by the issuer with a trust-listed key, re-signed at least every 5 minutes and at once on any
  change
- One credential type per list, randomised indexes, and at least 131,072 entries for herd privacy

**The worst-case withdrawal time is unchanged:** publication within 5 minutes, plus the verifier's cache (at most 5
minutes). A relying party that adds its own cache, such as Valet's registry cache, adds that time on top and must
say so.

## 8. Verification checks, revised

The eight checks keep their order and reason codes:

1. **The KB-JWT.** It is `kb+jwt`; `aud` is this relying party; the nonce is live here; it is within 120 seconds of
   `iat`; and `sd_hash` matches the presented SD-JWT. The nonce is not consumed yet.
2. **Trust list first.** Confirm the trust list names the credential's `iss` before fetching anything. If it
   doesn't, return check 4's result.
3. **The issuer's signature.** Verify the Agent Credential with a key that is in both the trust list and the
   issuer's JWT VC Issuer Metadata. Verify every disclosure digest. Only then consume the nonce, atomically.
4. **Accreditation.** The trust registry accredits the issuer for `vct` and `tier`.
5. **Validity and status.** Check the validity window and lifetime maxima, then check `status` **and**
   `operator_status`, under degraded-mode policy.
6. **Key binding.** The KB-JWT is signed by `cnf.jwk`, or by the last grant's key for a sub-agent (grant rules
   unchanged). The key has a logged `add` event and no earlier `retire` or `compromise`.
7. **Disclosure.** Every claim the route requires is disclosed. This replaces v0.4's Operator Credential matching,
   which is no longer needed.
8. **Relying-party policy.** Unchanged.

## 9. Moving to v0.5 in code

The staging network is alpha, so v0.5 is a clean cut: staging is reset, and no v0.4 credential is accepted after
the switch. Work goes package by package, each in its own pull request, with conformance vectors first so each
package is built against the same tests.

| Step | Package | Work |
|---|---|---|
| 1 | `conformance` | New vectors: SD-JWT+KB presentations, disclosures, Token Status Lists, key events, known-assistant entries, the client-attestation form |
| 2 | `verify` | SD-JWT VC parsing and disclosure checking (the OpenWallet Foundation `sd-jwt` Python library, or our own small implementation if its licence or footprint doesn't fit), JWT VC Issuer Metadata, the Token Status List, key-event checks, the revised checks |
| 3 | `issuer` | ACME-A changes (§4), SD-JWT VC signing, Token Status Lists, key-event log entries, known-assistant issuance |
| 4 | `vbot` | CIMD generation and hosting, SD-JWT+KB presentations, key events, the client-attestation form |
| 5 | `sidecar`, `integrations/keycloak`, `integrations/aws-lambda`, `sandbox` | New token types and headers; Keycloak client authenticator for pattern C |
| 6 | `e2e`, `deploy` | Local demo end to end on v0.5 |
| 7 | Veridact Valet | Replace `StaticRegistry` with a Veridact adapter on the sidecar; known-assistant entries for Lane A; pattern C for Lane B |

## Questions for review

1. Is the transparency-log key-event mechanism (§1.3) enough to replace did:webvh pre-rotation for Organisation-tier
   operators, or should Organisation tier also require operator keys in an HSM attested at onboarding?
2. Should the Delegation Credential stay a separate SD-JWT VC, or become claims inside the ACME-A order signed by the
   approvers?
3. Who issues known-assistant entries in production: every accredited issuer, or one designated by the
   governance authority?
4. Should pattern C replace pattern A for banks that support it, or sit beside it?
