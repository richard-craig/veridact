# Proposed changes for v0.4: sub-agents, actors, certificates and archival verification

Status: **accepted** · 19 November 2026 · incorporated into [specification v0.4](../specification.md)

These four proposals come from reading the IIW 42 proceedings (April 2026) against v0.3. Each one closes a gap
that other groups at IIW are already solving their own way. If Veridact leaves them open, relying parties and
integrators will each choose differently. Unlike the v0.2 and v0.3 gap lists, these are not choices already made
in the reference implementations. They are new design: the specification is ahead of the code until
`veridact-verify`, the issuer, vbot, the Keycloak bridge and the conformance vectors catch up.

## Decisions made on review

| Question | Decision |
|---|---|
| Should the Valet shape be stated here? | Yes. Item 2 defines it: the bank customer in `sub`, the agent in `act` |
| May the TLS key equal the `cnf` key? | Yes, allowed but not required. A separate `authentication` key is also accepted |
| Bring-your-own CA for Organisation-tier operators | Deferred |
| Default certificate lifetime | One hour by default, with shorter lifetimes recommended by risk profile (item 3) |
| Who re-timestamps archival records (RFC 4998)? | The relying party, as part of keeping its own records |
| Where does POPIA retention guidance live? | In the specification, because Veridact is built for South Africa |
| Must every Agent Credential be in the transparency log? | Yes. Archival verification always has log evidence for both credentials |

Still open, and not blocking: adopting Tenuo's token format if the OAuth WG takes it up (item 1), grants that
narrow `environment` or tier (item 1), and following the actor profile draft if its claim names change (item 2).

All four are additive. A v0.3 verifier still fails closed on everything below: it rejects a sub-agent presentation
(the signing key is not in the agent DID's `authentication`), it ignores `act`, and it never sees certificates or
verification records.

## 1. Sub-agents: attenuated grants, not new DIDs

**Gap.** Delegation has one hop, from operator to agent. An agent that spawns sub-agents has three options under
v0.3, and all of them are bad. It can share its key, which breaks accountability. It can give each sub-agent a DID
and an Agent Credential, which floods the issuer and the transparency log with identities that live for minutes.
Or it can proxy every call itself, which won't scale. At IIW 42 the OAuth sub-agent session (the "Waffles", formerly
"French Toast", tokens) and Tenuo (`draft-niyikiza-oauth-attenuating-agent-tokens`) both proposed the same shape:
each hop signs a narrower token for the next, and the chain verifies offline. The agent taxonomy session drew the
line that this proposal follows. An agent *class* is durable and gets an identity. An agent *instance* is
temporary and gets a grant.

**Today.** Nothing. A sub-agent has no way to act under its parent's credential.

**Proposed text.** Add a **Sub-agent Grant**. It is a compact JWS, ES256, `typ: veridact-subgrant+jwt`, signed by
the parent's key: on the first hop, the key the Agent Credential's `cnf` names; on later hops, the key in the
previous grant's `cnf`.

```json
{
  "iss": "<agent DID>",
  "cred": "<Agent Credential id, first hop only>",
  "prev": "<base64url SHA-256 of the previous grant's compact JWS, later hops only>",
  "jti": "<uuid>",
  "cnf": { "jwk": { "kty": "EC", "crv": "P-256", "x": "…", "y": "…" } },
  "scopes": ["fs:claims:read-status"],
  "limits": { "currency": "ZAR", "perPayment": "200.00", "perDay": "500.00" },
  "audiences": ["https://api.bank.example"],
  "iat": 1795075200,
  "exp": 1795076100
}
```

`iss` is the root agent DID on every hop. The sub-agent signs the Agent Presentation with its own key, carries the
chain root-first in `veridactGrants`, and sets the presentation's `kid` to the JWK Thumbprint URI (RFC 9278) of the
last grant's `cnf` key. `holder` stays the agent DID.

The verifier adds one check after the Agent Credential checks pass:

| Rule | On failure (logged) |
|---|---|
| The first grant is signed by the Agent Credential's `cnf` key, its `cred` equals the credential's id, and it has no `prev` | `GRANT_SIGNATURE` |
| Each later grant is signed by the previous grant's `cnf` key, and its `prev` matches the previous grant | `GRANT_SIGNATURE` |
| `iss` equals the agent DID on every grant | `GRANT_SIGNATURE` |
| `scopes` is a subset of the parent's (the first hop's parent is the credential's scopes after trust list filtering) | `GRANT_WIDENS_SCOPE` |
| Per currency, `perPayment` and `perDay` are at most the parent's, and no grant adds a currency its parent lacks | `GRANT_WIDENS_LIMIT` |
| `audiences` is a subset of the parent's and includes this relying party | `GRANT_WIDENS_AUDIENCE` |
| `exp` is no later than the parent's or the Agent Credential's, and `exp − iat ≤ subAgentGrantMaxLifetime` | `GRANT_EXPIRED` |
| The chain is no longer than `maxSubAgentDepth` | `GRANT_TOO_DEEP` |
| The presentation is signed by the last grant's `cnf` key | `GRANT_SIGNATURE` |

Every failure returns the public code `AUTH_FAILED`. Unlike unknown scopes in a credential, a widening scope is
never dropped quietly: a grant that tries to widen is either broken or hostile.

The trust list's `policy` gains `maxSubAgentDepth` (default 2; 0 disables sub-agents) and
`subAgentGrantMaxLifetime` (default 900 seconds).

**Limits.** The root agent's `perDay` is a budget shared by the whole family, so the relying party counts payments
by any sub-agent against the agent DID. The last hop's `perDay` is a budget of its own, which the relying party
tracks by the last grant's key thumbprint. An intermediate hop's `perDay` only caps what its children may be given.
It is not a shared budget, so two sibling sub-agents can together spend more than their parent's daily limit, but
never more than the root's. The verifier takes both paid-today figures and reports the agent DID and the last key
thumbprint so the relying party can keep both ledgers.

**Revocation.** Grants have no status entry. They are revoked by expiry (at most 15 minutes by default) or by
revoking the Agent Credential, which ends the whole family at once.

**Audit.** Grants never pass through the issuer or the transparency log. Relying parties log the SHA-256 of the
grant chain alongside the agent DID, so the operator can work out from its own records which sub-agent acted.

**Pattern A.** The `subject_token` is the presentation, grants included. The DPoP key must be the last grant's
`cnf` key. The issued token nests the sub-agent in `act` (see item 2).

**Open questions.**
- Should Veridact adopt Tenuo's token format if the OAuth WG takes it up, rather than keep its own? The rules
  above are deliberately close to it.
- Should a grant be able to narrow `environment` or tier? So far there is no case for it.

## 2. Pattern A: the agent is the actor, not the subject

**Gap.** The Keycloak bridge issues an access token after token exchange, but the spec doesn't say whom the token
names. One integrator will put the agent DID in `sub`. Another will put the operator there and forget to say an
agent is involved. "Agents: Subject or Client?" at IIW 42 found exactly this confusion, and pointed to Karl
McGuinness's actor profile (`draft-mcguinness-oauth-actor-profile`). That draft formalises the `act` claim already
defined in RFC 8693 §4.1.

**Today.** The bridge passes Keycloak a JWT Authorization Grant (RFC 7523) and leaves the claims to Keycloak's
defaults.

**Proposed text.** An access token issued in pattern A carries:

```json
{
  "iss": "https://auth.bank.example",
  "sub": "<operator DID>",
  "act": { "sub": "<agent DID>" },
  "scope": "fs:claims:read-status",
  "cnf": { "jkt": "<thumbprint of the DPoP key>" },
  "veridact": {
    "tier": "organisation",
    "agentCredential": "urn:uuid:…",
    "operatorCredential": "urn:uuid:…",
    "limits": { "currency": "ZAR", "perPayment": "500.00", "perDay": "2000.00" }
  },
  "exp": 1795076100
}
```

- `sub` is the operator DID: the party whose authority is being used, and the one accountable for it.
- `act.sub` is the agent DID. With sub-agents, `act` nests the RFC 8693 way, with the current actor outermost:
  `{"sub": "urn:ietf:params:oauth:jwk-thumbprint:sha-256:<jkt>", "act": {"sub": "<agent DID>"}}`.
- `scope` and `veridact.limits` are the most the token allows: the presentation's (or the last grant's), narrowed
  by the request.
- `exp` is no later than the Agent Credential's, the Operator Credential's, or any grant's.
- Introspection returns the same claims.

Add a normative rule: **a resource server must not treat a token that carries `act` as if the subject were acting
directly.** The operator's own permissions at the relying party never flow to its agent. Only `scope` and `limits`
apply. Without this rule, `sub` = operator becomes a confused-deputy bug waiting to happen.

The reason for putting the operator in `sub` rather than the agent: the limits, the accountable role and the audit
question ("who did this?") all belong to the operator. Resource servers also already authorise by organisation. An
agent in `sub` would look like a new customer, and integrators would end up giving it standing permissions.

**Keycloak.** The bridge puts `act` and `veridact` into the RFC 7523 assertion, and a protocol mapper copies them
into the access token. Both go into the bridge's tests.

**Agents acting for a bank customer (Veridact Valet).** The same shape applies when the principal is a person
rather than the operator:

- `sub` is the bank's own identifier for the customer, as its authorisation server already issues it. It is
  never a Veridact identifier, because Veridact never holds customer identities.
- `act.sub` is the agent DID, nested as above for sub-agents.
- `scope` is the intersection of the agent's Veridact scopes and what the customer consented to.
- `veridact.limits` is the lower of the delegation limits and the customer's consented limits, per currency.
- The bank's consent record, not Veridact, is the authority for what the customer allowed. The token adds
  `consent` (the bank's consent id), so a resource server can log which consent the agent used.
- The rule above holds here as well: the customer's own permissions never flow to the agent. Only `scope` and
  `limits` apply.

**Open question.** If the actor profile draft changes the claim names, Veridact follows the draft. RFC 8693's
`act` already exists, so v0.4 isn't blocked waiting for it.

## 3. Agent Certificates: the agent DID in an mTLS client certificate

**Gap.** Bank API gateways already terminate mutual TLS, and many already bind tokens to client certificates
(RFC 8705, as FAPI requires). Under v0.3 a gateway has to run a verifier before it learns anything about an agent.
At IIW 42, NodeX's "DID-Backed X.509" proposal put a DID URL in the certificate's SAN so that existing PKI and TLS
stacks carry the DID without changes. Veridact already speaks ACME, so it can issue such a certificate with little
extra work, and a gateway can then identify the agent with nothing but its truststore.

**Today.** Veridact issues only `vc+jwt`.

**Proposed text.**

*Issuance.* `new-order` takes optional `formats` (default `["vc+jwt"]`) and, with `"x509"`, an optional
`certificateLifetime` in seconds. When `formats` includes `"x509"`, the finalize request carries the key-binding
JWT as today plus `csr` (base64url DER, as in RFC 8555). The CSR's key must be one of the agent DID's
`authentication` keys in the DID log's current version. It may be the same key the Agent Credential's `cnf`
names, which keeps agent key management simple, or a separate TLS key. The issuer checks that, then adds a
`veridactX509` URL to the order that serves `application/pem-certificate-chain`.

*Certificate profile.*
- Issued by the issuer's **Veridact Agent CA**, one per issuer and environment. This is never a Web PKI CA.
- An empty subject, and exactly one SAN, a URI holding the agent DID. The SAN is critical, as RFC 5280 requires
  when the subject is empty.
- Extended key usage `id-kp-clientAuth` only.
- A non-critical `VeridactBinding` extension:
  `SEQUENCE { operatorDid UTF8String, agentCredentialId UTF8String, tier UTF8String }`.
  The OID needs a private enterprise number assigned by IANA.
- `notAfter` no later than the Agent Credential's `exp`, nor than `notBefore` plus the smallest of the requested
  `certificateLifetime`, the delegation's `certificateMaxLifetime` if it sets one, and the trust list's
  `agentCertificateMaxLifetime` (default 3600 seconds).
- No CRL distribution point and no OCSP. Short lifetimes take their place.

*Choosing a lifetime.* One hour is the default and the ceiling, not the recommendation for every agent. How long a
stolen certificate stays useful to an identity-only gateway equals its lifetime, so operators should go shorter
as the risk rises, and relying parties can enforce that by refusing certificates older than their route allows:

| Agent profile | Recommended lifetime |
|---|---|
| Read-only scopes, non-exportable key (KMS, TPM, HSM) | Up to 1 hour (the default) |
| Software key (Domain tier only) | 15 minutes |
| Any scope that changes data, or quotes and claims submission | 15 minutes |
| Payment scopes, or an agent that can spawn sub-agents | 5 minutes |
| An agent under investigation, or after a suspected compromise | Revoke instead; do not renew |

Renewal through ARI makes short lifetimes cheap: vbot renews at two thirds of the lifetime, as it does for
credentials. A delegation can set `certificateMaxLifetime` so an approver fixes the ceiling for a risky agent.

*Trust distribution.* Each issuer entry in the trust list gains `x509Roots`, a list of
`{ "certificate": "<base64 DER>", "notBefore": …, "notAfter": …, "environment": "…" }`. The governance key signs
these roots along with everything else, so certificates add no second root of trust. `veridact-verify
export-truststore` writes a gateway truststore from a verified trust list.

*Which revocation wins.* The Agent Credential's status always wins. A certificate is valid only while all four
hold: its chain is valid, it is within its validity period, the Agent Credential it names is not revoked or
suspended, and its key is still in the agent DID's `authentication`. Relying parties choose one of two profiles:

| Profile | Checks | Revocation delay | Allowed |
|---|---|---|---|
| Identity only | Chain and validity only | Up to the certificate's lifetime | Authentication and read scopes. **Never payment scopes**, because the 5-minute revocation rule can't be met |
| Full | Also the Agent Credential's status and the DID log | As for credentials (5 minutes plus cache) | Everything |

*Authentication, not authorisation.* A certificate says which agent it is and which operator it belongs to.
Scopes and limits still come from a presentation or a pattern A token. To make the two meet, extend pattern A:
when the client authenticates with an Agent Certificate whose SAN equals the presentation's `holder`, the token
may be certificate-bound (`cnf: { "x5t#S256": … }`, RFC 8705) instead of DPoP-bound. This relaxes v0.3 item 12 to:
"the binding key must be one of the agent DID's `authentication` keys: for DPoP, the `cnf` key; for mTLS, the
key of an Agent Certificate naming the agent DID, which may itself be the `cnf` key."

*One key for TLS and JWS.* Using the `cnf` key for TLS is allowed because TLS 1.3 signs `CertificateVerify` over
a fixed context string, and a JWS signs a base64url-encoded header and payload, so a signature made for one
cannot be passed off as the other. Gateways must negotiate TLS 1.3 for Agent Certificates. Operators that keep
TLS keys on different hardware from signing keys (a load balancer, for example) use a separate
`authentication` key.

*Why not NodeX's proof-of-possession extension.* A PoP extension proves the key belongs to the DID when the CA
can't vouch for it. Here the CA is the Veridact issuer, which checks the binding at issuance through the DID log
and the key-binding JWT. A PoP extension only becomes worth adding if operators may bring their own CAs, which is
deferred.

## 4. Archival verification: "valid now" versus "was valid at time T"

**Gap.** Verification answers "may this agent act now?" A payment dispute three years later asks something
different: "was this agent authorised when it acted?" Under v0.2, removing a key from the trust list invalidates
everything it signed, which is right for live traffic and wrong for evidence. Status lists are also re-signed
every 5 minutes and nothing keeps the old ones. The CAWG session at IIW 42 defined an "archival-quality credential"
as one whose link to its subject can be verified at any time after the claim, and that is the standard financial
disputes need. In South Africa, FICA requires records to be kept for at least five years, and insurers and FAIS
providers keep theirs similarly long.

There is also a subtlety that rules out naive fixes. **A compromised key can sign with any `iat`.** "It was signed
before the compromise" is only believable if the evidence of time comes from someone other than the signer.

**Today.** The reference verifier returns a live decision and keeps nothing.

**Proposed text.**

*Two anchors of time.* Every Agent and Operator Credential is in the transparency log before it is released, so
a credential's log inclusion (the first signed tree head that covers its entry) is evidence of when it existed,
independent of the issuer key that signed it. That anchors the credentials. The presentation, the grants and the
status lists the verifier used are not logged, so the relying party anchors them by timestamping its record.

*Verification Record.* The verifier can emit a self-contained record. A relying party must keep one for every
decision on a payment scope, and may keep them for other decisions:

```json
{
  "type": "VeridactVerificationRecord",
  "verifiedAt": "2026-11-19T07:30:00Z",
  "verifier": "veridact-verify/0.4.0",
  "decision": "allow",
  "reasons": [],
  "request": { "action": "fs:payments:initiate", "amount": "350.00", "currency": "ZAR", "paidToday": "800.00",
               "reference": "<the relying party's own transaction reference>" },
  "presentation": "<compact JWS, grants included>",
  "trustList": "<the trust list JWS used>",
  "didLogs": { "<DID>": { "versionId": "…", "log": "<did.jsonl up to that version>" } },
  "statusLists": { "<status list URL>": "<the status list JWS as fetched>" },
  "logReceipts": { "<credential id>": "<Veridact-Log-Receipt value with its inclusion proof>" },
  "timestamp": "<RFC 3161 token over SHA-256 of the record without this field>"
}
```

The record holds every artefact that was fetched, so verifying it later needs nothing online. `logReceipts` must
cover both credentials. The `timestamp` comes from a time-stamping authority, or from the relying party's own
append-only log, and is required: it is the only evidence of the presentation's time that the agent's own keys
cannot forge.

*Retiring keys versus compromised keys.* Today, removing a key from the trust list means one thing. In v0.4 it
means two things:
- **Retirement.** A key may leave the live list once nothing it signed can still be live (`notAfter` plus the
  longest credential lifetime). Live verification is unchanged.
- **Compromise.** Governance also publishes an **archive list** at `{iss}/archive`, signed with the same governance
  key. It holds every key ever listed, is kept for as long as the network runs, and adds `compromisedAt`
  (NumericDate) to any key that has been compromised. If the time of compromise is unknown, `compromisedAt` is the
  key's `notBefore`, which invalidates everything it ever signed, exactly as v0.2 does today.

*Archives.* For the trust list's `archiveRetention` (default 5 years):
- Issuers keep every status list version whose bits changed, and serve it at `{list URL}?version={n}`.
- Governance serves every trust list version at `{iss}/versions/{version}` and never changes them.
- The transparency log keeps its entries and tree heads for at least `archiveRetention`.
- Issuers keep hosted DID logs even for deleted agents. did:webvh logs are already append-only.

Relying parties' records are the main copy, and must be self-sufficient. These archives are the backup.

*Historical verification.* `veridact-verify verify-record --at <time>`:
1. **Check both anchors.** Verify each credential's log receipt, giving `T_cred` for that credential: the time of
   the first signed tree head that covers it. Verify the record's `timestamp`, giving `T_rec`. A missing or
   invalid receipt or timestamp gives `indeterminate` with `NO_LOG_EVIDENCE` or `NO_INDEPENDENT_TIME`.
2. **Repeat checks 2 to 7 against the artefacts in the record**, with the clock set to `verifiedAt`. Nonce reuse
   can't be rechecked later, so the relying party's own log is the evidence that the nonce was used once.
3. **Fetch the current archive list.** If the key that signed a credential has `compromisedAt ≤ T_cred` for that
   credential, or the key that signed a status list or the trust list has `compromisedAt ≤ T_rec`, the result is
   `invalid_at_time` with `KEY_COMPROMISED_BEFORE`. A compromise discovered later but dated after the anchor
   doesn't affect the record.
4. **Take status from the status lists in the record.**

The result is one of `valid_at_time`, `invalid_at_time` (with a reason) or `indeterminate` (naming the missing
evidence). These are archival results only. They never feed live allow or deny decisions.

*Keeping records verifiable.* Keeping its records verifiable for their whole retention period is the relying
party's job, not a governance service. Before the algorithm behind a record's timestamp, or ES256 itself, stops
being trusted, the relying party renews the record's evidence by re-timestamping it with a stronger algorithm,
preferably as an evidence record (RFC 4998). Governance publishes an advisory, with a date, when an algorithm used
in the network should be renewed.

*Records and POPIA.* The specification states this guidance because Veridact is built for South Africa. Each
relying party confirms it in its own legal review.

| POPIA condition | What it means for verification records |
|---|---|
| Responsible party | The relying party is the responsible party for its records. Records never go to Veridact or to issuers |
| Minimality (section 10) | `request` holds the action, amount, currency, paid-today figure, the relying party's own reference and, where there is one, the bank's consent id. Never account numbers, customer names, ID numbers or free text. Credentials name roles, never people |
| Retention (section 14) | Keep records for as long as the relying party's record-keeping obligations require: for example, the five years FICA (section 23) requires after a single transaction or the end of a business relationship. Then destroy or de-identify them. Records of non-payment decisions follow the relying party's normal log retention |
| Security safeguards (section 19) | Append-only storage, access limited to fraud, disputes and audit, and integrity protected by the timestamp |
| Cross-border transfers (section 72) | Store records in South Africa, or transfer them only under section 72 |

In Veridact Valet deployments the customer's identifier appears in the bank's access token, not in the
presentation, so a record contains no customer identity. The bank's consent id goes in an optional `request.consent`.
